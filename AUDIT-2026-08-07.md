## Critical

### C1. Полный stdin сессии пишется в общедоступный файл при каждом рендере
`statusline.sh:20` · уверенность 90 · раздел 1.3 Sensitive Data Exposure

```bash
# Dump raw input for debugging
echo "$input" > /tmp/statusline-input.json
```

Отладочная строка, оставшаяся в рабочем коде. Файл создаётся с правами `-rw-r--r--` в общем `/tmp`, то есть читается любым процессом и любым пользователем машины. Содержимое — не только путь и токены: там `session_id`, `session_name`, `prompt_id`, `cwd` и, что существеннее всего, **`transcript_path`** — указатель на файл с полной историей твоего диалога с Claude. Утечка самого дампа даёт готовую наводку, где лежат транскрипты.

Второй аспект — фиксированное предсказуемое имя в разделяемом каталоге. Классический вектор: посторонний процесс заранее создаёт `/tmp/statusline-input.json` симлинком на чужой файл, и скрипт перезаписывает цель твоими правами.

Третий — запись происходит на **каждый** рендер статуслайна, то есть постоянно в течение всего рабочего дня.

**Чинится так:** строку удалить. Если дамп нужен для отладки — включать его переменной окружения (`[[ -n "$STATUSLINE_DEBUG" ]] && ...`), писать в `$HOME/.cache/` и ставить `umask 077` перед записью.

- [x] исправлено — ровно так: дамп под `[[ -n "$STATUSLINE_DEBUG" ]]`, пишется в `$HOME/.cache/statusline-input.json` с `umask 077` (проверено: `-rw-------`). По умолчанию в `/tmp` не пишется ничего.

  Поправка: первая версия этой правки уронила `mkdir -p "$CACHE_DIR"`, который жил в удалённом API-слое. При включённом `STATUSLINE_DEBUG` на машине без `~/.cache` запись падала, и текст ошибки уходил в stderr — то есть прямо в строку статуса. Каталог теперь создаётся на месте, весь блок заглушён `2>/dev/null`. Проверено на трёх случаях: каталога нет, каталог недоступен на запись, обычный режим.

### H1. Весь слой обращения к API избыточен — эти данные уже приходят в stdin


Сверка живых данных на момент аудита:

**Чинится так:** читать `.rate_limits.*` из того же `$input`, что и остальные поля. Форматирование оставшегося времени считать от `resets_at` вычитанием `$(date +%s)`. `statusline-claude-usage.sh` удалить.

**Проверено 2026-08-07 перед правкой:** `rate_limits` в stdin есть (CLI 2.1.224), `resets_at` сходится с API до секунды. ### H4. Ответ с ошибкой кэшируется как валидный и отравляет кэш на две минуты

## Medium

### M1. Имя каталога подставляется в форматную строку `printf`
`statusline.sh:45` · уверенность 90 · раздел 2.2 Type Issues

```bash
dir_part=$(printf " ${C_DARK_GRAY}${dir_parent}/${C_BLUE}${dir_name}${C_RESET}")
```

`$dir_parent` и `$dir_name` попадают в **первый** аргумент `printf`, то есть в форматную строку. Любой `%` в имени каталога будет истолкован как спецификатор: в `~/tmp/100%done` `printf` увидит `%d`, не найдёт аргумента и напечатает `0`. Обратный слэш обработается как escape. Путь пользователь задаёт произвольный, так что входные данные тут неконтролируемые.

Отдельно любопытно, что CLAUDE.md предупреждает ровно про этот класс ошибок — «Don't use `printf` with captured output containing `%` symbols» — но в самом коде приём остался.

**Чинится так:** `printf ' %b%s/%b%s%b' "$C_DARK_GRAY" "$dir_parent" "$C_BLUE" "$dir_name" "$C_RESET"` — данные уходят в аргументы, формат остаётся литералом.

- [x] исправлено. Воспроизведено на каталоге `100%done`: старый код печатал `1000one`, новый — `100%done`. Заодно так же переписан `git_part` — имя ветки такие же неконтролируемые данные, как путь.
